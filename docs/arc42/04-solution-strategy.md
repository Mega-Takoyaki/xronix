# 解決戦略

| 課題 | 戦略 | 関連ADR |
| --- | --- | --- |
| 固定費を避ける | VPC外のLambda、DynamoDBオンデマンド、HTTP API、CloudFront標準ドメイン | 0007 |
| 二重投稿の防止 | 送信前に状態を `sending` へ条件付き更新。create は1回だけ呼び、結果不明は `unknown` にして人が確認 | 0006 |
| トークンの入れ替わり | トークン更新は1つの関数に集約し、DynamoDBの条件付き書き込みでリースを取る | 0003 |
| 分類・返信案 | 既定はBedrock（IAM認証）。OpenAIも選べる。AIが使えないときは、ルールとテンプレートに戻る。スパム・要注意はAIに送らない | 0011 |
| アカウントの保護 | 日次上限、ブロック対象、緊急停止、リンク禁止を送信Lambdaで強制する | 0009（予定） |
| 運用者の手間 | 承認画面は一覧→承認／編集／却下だけ。説明はⓘに集約 | — |
| 再現性 | IaCで全リソースを定義。Lambdaはローカルでテスト可能な構造にする | 0001 |

## 設計原則

- 取得は冪等にし、読み取りだけを指数バックオフでリトライする。
- 状態遷移はDynamoDBの条件付き書き込みで守る。
- 人が決められることは人に任せる。確認機能を足しすぎない。
- Lambdaの非同期呼び出しは、再試行回数を0にする（送信経路で勝手に再実行されないため）。
