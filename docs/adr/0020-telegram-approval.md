# ADR-0020 Telegramで、承認待ちを受け取り、承認・却下する

状態: 採用　日付: 2026-10-18

## 背景

承認の操作を、画面を開かずに、通知の場所（Telegram）で済ませたい。これまでの通知は、プライバシーのため、件数だけで、本文を載せていなかった（arc42 第8章）。

## 決定

| 項目 | 内容 |
| --- | --- |
| 通知の内容 | 運用者が、設定で明示的に有効にしたときだけ、本文の全文（相手の投稿と返信案）を、Telegramに送る。長い本文は、1つあたり1500文字で切る。既定は無効（件数だけ） |
| ボタン | 「承認して送信」「却下」（インラインボタン）。返信案の書き換えは、画面で行う |
| 結果の表示 | 押した結果を、そのメッセージ上に書き（「承認して送信しました」「却下しました」「送信できませんでした: 理由」）、ボタンを消す。画面で処理した場合も、同じメッセージに結果を書く |
| 受信の仕組み | Telegramの Webhook。`POST /api/telegram/webhook` を、認証なしの経路にする（API Gatewayのルートに `Authorizer: NONE`）。有効にするとき、`setWebhook`（宛先は、画面のURL＋`/api/telegram/webhook`、`allowed_updates` は `callback_query` だけ）を登録する。無効にすると `deleteWebhook` |
| 呼び出しの確認 | ①登録時に作った合言葉（`secret_token`、SSMに保存）が、ヘッダー `X-Telegram-Bot-Api-Secret-Token` と一致すること。②押した人のユーザーIDが、許可したユーザーIDと一致すること。③押されたチャットが、設定したチャットであること。どれか1つでも違えば、何も実行しない（①は403、②③は、通知だけ返して無視） |
| 許可するユーザー | 個人のチャットなら、チャットID＝ユーザーID。グループのチャットは、別に、許可するユーザーIDを設定する（未設定なら有効にできない） |
| 承認の処理 | 画面と同じ処理（`/api/mentions/:id/reply`、`reject`）を通る。上限・ブロック・緊急停止・リンク禁止の検査と、送信キューの設定も、同じ。投稿は再試行しない |
| 二重の操作 | 状態が承認待ちのときだけ動く。同じボタンを何度押しても、1回だけ送る |
| 検査で止まった場合 | Xには何も送らず、理由を表示し、ボタンは残す |
| 件数の多いとき | 1回のジョブで、個別に送るのは10件まで。超えた分は、件数でまとめて知らせる。返信文が空（人が書く）ものも、件数で知らせる |

## 結果と制約

- 本文が、Telegramのサーバーを通る。Telegramのボットのチャットは、エンドツーエンドの暗号化ではない。
- Webhookを登録している間は、`getUpdates`（チャットIDの自動検出）が使えない。無効にすれば、戻る。
- 画面のURLは、CloudFrontのURL（https）が必須。
- 承認待ちが多いと、通知も多くなる。
- 実機のTelegram・AWSでの動作（Webhookの到達、ボタンの操作）は、デプロイ後に確認する。
