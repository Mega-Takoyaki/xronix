# ADR-0003 トークンの保管と更新の排他制御

状態: 提案中　日付: 2026-10-12

## 背景

リフレッシュトークンは使うたびに入れ替わる。古い値で更新すると失敗し、再認可が必要になる。同時に複数のLambdaが更新すると壊れる。

## 保管先の比較

| 案 | 費用 | 長所 | 短所 |
| --- | --- | --- | --- |
| SSM SecureString（標準） | 無料 | 暗号化、IAM制御、PutParameterで上書き可 | 条件付き書き込みが無い。排他は別途必要 |
| Secrets Manager | 約$0.4／月／シークレット | 世代管理 | 費用。ここでも排他は別途必要 |
| DynamoDB（暗号化は既定で有効） | ほぼ無料 | 条件付き書き込みで更新と排他を同じ場所で行える | 運用者の方針（Secrets／SSM）から外れる |

## 決定（提案）

- クライアントIDとシークレットは SSM SecureString。
- 入れ替わるトークン一対は SSM SecureString に置く。更新の排他は DynamoDB のリース（条件付き書き込み）で行う。
- 取得できなかった呼び出しは待ってから、SSMを読み直す。

## 注意

- 保存の失敗が最大の危険点である。リフレッシュ成功後、保存に失敗すると旧トークンが無効なまま残る。保存は再試行する（リフレッシュ自体は再実行しない）。
- 実装前に、リース期限、待機時間、失敗時の再認可手順を詰める。

## 代替

排他と値を1か所に集める簡潔さを優先するなら、DynamoDB に値を置く案もある。運用者の判断を仰ぐ。
